# План реализации суммаризатора сообщений Telegram

> Суммаризатор работает как **личный пользовательский аккаунт** через Telethon.  
> Читает сообщения из выбранных каналов/чатов, суммаризирует через **GigaChat API**  
> (Sber, совместим с OpenAI SDK) и присылает результат в личную переписку пользователя.

---

## 1. Архитектура

```
Telethon Client (личный аккаунт пользователя)
       │
       ├──► Читает сообщения из выбранных чатов/каналов
       │
       ├──► Обрабатывает команды от пользователя (/summarize, /chats, /schedule)
       │
       └──► Отправляет суммаризацию в ЛС пользователя
       │
       ▼
SQLite (хранилище) ──► LLM API (облачная модель)
```

**Ключевые решения:**
- Один клиент — Telethon (авторизация по номеру телефона)
- Нет бота — команды обрабатываются через Telethon
- Облачная LLM — **GigaChat** (YandexGPT/ЯндексGPT)
- SQLite — лёгкое хранилище без дополнительных сервисов
- Docker — одиночный контейнер, без Redis и PostgreSQL

### 5.2. Вызов LLM (GigaChat API)

**Авторизация:**
- Получение токена доступа через `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth`
- Токен действует 30 минут, требуется обновление
- Параметры: `RqUID` (уникальный идентификатор запроса), `Authorization` (Bearer ключ), `scope=GIGACHAT_API_PERS`

**Интеграция через OpenAI SDK (рекомендуется Sber):**
- Base URL: `https://api.giga.chat/v1`
- Совместимость с OpenAI Chat Completions API
- Доступные модели: `GigaChat-2`, `GigaChat-2-pro`, `GigaChat-2-lite`
- Лимит токенов: 50000 в день (настраивается в DAILY_TOKEN_LIMIT)

- [ ] Интерфейс `llm_client.py`:
  - [ ] Получение и кэширование токена (автоматическое обновление каждые 25 минут)
  - [ ] Вызов GigaChat через OpenAI SDK совместимость
  - [ ] Retry-логика при ошибках API (429, 500, 503)
  - [ ] Логирование запросов и потребления токенов
  - [ ] Fallback на другую модель при сбое

- [ ] Промпт-инжиниринг (`prompts.py`):
  - [ ] Шаблон краткого резюме (1-2 абзаца)
  - [ ] Шаблон тезисного конспекта
  - [ ] Шаблон multilingual-суммаризации

- [ ] Рекомендуемая модель для MVP: `GigaChat 2 Lite` (быстрая, дешёвая)

### 5.3. Отправка результата
- [ ] Отправка суммаризации в `OWNER_CHAT_ID` (личная переписка)
- [ ] Разбиение длинных сообщений на части

## 6. Команды в ЛС

| Команда | Короткая | Описание |
|---------|----------|----------|
| `/start` | `/s` | Приветствие, описание возможностей |
| `/my_id` | `/id` | Вывести ваш ID для настройки OWNER_CHAT_ID |
| `/chats` | `/c` | Список подключённых чатов, включение/выключение |
| `/active` | `/a` | Список активных чатов |
| `/add_chat` | `/ac` | Добавить чат в активные: `/ac <ID>` |
| `/rm_chat` | `/rc` | Убрать чат из активных: `/rc <ID>` или `/rc all` |
| `/add_all` | `/aa` | Активировать все чаты |
| `/summarize` | `/sum` | Ручная суммаризация: `/sum 50` (50 сообщений) |
| `/schedule` | `/sch` | Настройка расписания (например, "ежедневно в 08:00") |
| `/status` | `/st` | Последний запуск, статус, ошибки |
| `/settings` | `/set` | Выбор формата резюме: `/set format:краткое` |

## 7. Хранение данных (SQLite)

### 7.1. Схема БД

**Таблица `messages`:**
- `id` — уникальный ID
- `telegram_id` — уникальный ID из Telegram (UNIQUE constraint, дедупликация)
- `chat_id` — ID чата/канала
- `chat_title` — название чата
- `content` — текст сообщения
- `timestamp` — дата/время (МСК, UTC+3)
- `processed` — флаг обработки (BOOL)

**Таблица `summaries`:**
- `id` — уникальный ID
- `chat_ids` — JSON-список чатов
- `period_start` — начало периода
- `period_end` — конец периода
- `summary_text` — текст резюме
- `format` — формат (short/detailed/bullet)
- `status` — статус (pending/success/error)

**Таблица `settings`:**
- `key` — ключ настройки
- `value` — значение
- Примеры: `schedule_time=08:00`, `format=detailed`, `active_chats=123,456`, `tokens_used:2026-10-28=50000`

### 7.4. Лимит токенов
- [x] Суточный лимит: 50000 токенов (настраивается в DAILY_TOKEN_LIMIT)
- [x] Хранение в БД: `settings.key = tokens_used:YYYY-MM-DD`
- [x] При достижении лимита — отправка уведомления пользователю
- [x] Автоматический сброс лимита каждый день

### 7.2. Хранение данных в Docker
